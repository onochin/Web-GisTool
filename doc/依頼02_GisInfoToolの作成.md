# webgis-tools：GIS Info ツール追加依頼

既存の `webgis-tools` プロジェクトに、新しいツールとして **「GIS Info」** を追加してください。

このプロジェクトは、

> QGISやCLIを起動しなくても、ブラウザだけで簡単なGIS処理・確認ができるツール群

を目指しています。

既存の座標変換ツールは維持し、今回2つ目のツールとして **Vector / Rasterの情報を確認できる「GIS Info」** を実装してください。

---

# 1. 今回の目的

GISファイルをブラウザへドラッグ＆ドロップするだけで、

* VectorかRasterか
* ファイル形式
* CRS / EPSG
* データ範囲
* Vector固有情報
* Raster固有情報

などを確認できるツールを作成してください。

Vector用とRaster用にツールを分けず、

**1つの「GIS Info」ツールで自動判定**

してください。

---

# 2. 基本方針

重要な方針：

* 処理は可能な限りブラウザ内で完結
* 独自バックエンドは使用しない
* ファイルを外部サーバーへアップロードしない
* GitHub Pagesなどの静的ホスティングで動作できること
* QGIS / Python / GDAL CLIなどを利用者側に要求しない
* Vector / Rasterを自動判定
* 読み込めない情報は推測しない
* 情報確認を主目的とし、UIを複雑にしない

---

# 3. Dashboardへの追加

既存のWebGIS Tools Dashboardへ、

* 座標変換
* GIS Info

の2つを表示してください。

GIS Infoカードから、

`/gis-info`

へ移動できるようにしてください。

既存のツール定義が `config/tools.ts` 等で管理されている場合は、その仕組みをそのまま使用してください。

Dashboardへ直接ハードコードしないでください。

---

# 4. GIS Infoページ

ルート：

`/gis-info`

ページ名：

**GIS Info**

説明：

`Vector / Rasterの基本情報をブラウザで確認`

程度の簡潔な説明を付けてください。

---

# 5. UIレイアウト【重要】

既存の座標変換ツールと統一感を持たせてください。

PC画面では、

**左側：情報表示**
**右側：ファイルドロップ**

の2カラム構成にしてください。

イメージ：

```text
GIS Info

┌──────────────────────┬─────────────────────────┐
│                      │                         │
│      情報表示         │      ファイルドロップ    │
│                      │                         │
│  ファイル情報         │                         │
│  CRS                 │   ファイルをここに       │
│  Vector/Raster情報   │      ドロップ            │
│                      │                         │
│                      │                         │
└──────────────────────┴─────────────────────────┘
```

左側をやや広くして構いません。

例：

* 左 55～60%
* 右 40～45%

程度。

スマートフォンなど狭い画面では上下配置に切り替えてください。

---

# 6. ファイルドロップ領域

右側に大きなドラッグ＆ドロップ領域を配置してください。

表示例：

`ファイルをここにドロップ`

その下に、

`またはファイルを選択`

を配置しても構いません。

ファイルをクリック選択する操作にも対応してください。

---

# 7. ドロップ後の動作

ファイルを読み込んだら、

**解析ボタンを押さなくても自動的に解析**

してください。

基本フロー：

```text
ファイルドロップ
      ↓
ファイル形式判定
      ↓
Vector / Raster判定
      ↓
メタデータ取得
      ↓
左側に情報表示
```

解析中は、

`解析中...`

などの状態が分かるようにしてください。

---

# 8. Vector / Raster自動判定

ファイルの拡張子だけで決めつけず、

可能な範囲で読み込んだデータから判定してください。

判定結果は左側の最上部に分かりやすく表示してください。

例：

`VECTOR`

または

`RASTER`

形式：

`GeoJSON`

`GeoTIFF`

など。

---

# 9. 共通情報

Vector / Rasterどちらの場合も、可能な範囲で以下を表示してください。

## ファイル

* ファイル名
* ファイル形式
* Vector / Raster
* ファイルサイズ

## CRS

* CRS名
* EPSGコード
* 座標単位
* Geographic / Projected

## 範囲

* X min
* X max
* Y min
* Y max

または、

* xmin
* ymin
* xmax
* ymax

のどちらかで統一してください。

日本の平面直角座標系の場合でも、表示方法が混乱しないよう注意してください。

---

# 10. CRSの扱い【重要】

ファイル内にCRS情報が存在する場合は、それを取得してください。

例えば、

* GeoTIFF → GeoKey等
* Shapefile → `.prj`
* GeoPackage → CRS / SRS情報
* その他、形式内にCRS情報があるもの

です。

CRS情報がない場合は、

**勝手に推測しないでください。**

表示例：

`CRS：不明`

としてください。

ただし、ファイル形式そのものに座標系の規約がある場合は、その根拠が分かる形で扱ってください。

例：

KML

→ WGS84

GeoJSONについても、仕様上の扱いとファイル内の実データを混同しないよう注意してください。

---

# 11. Vectorの場合

Vectorと判定した場合は、以下を可能な範囲で表示してください。

## データ情報

* Geometry Type
* Feature数
* Z座標の有無
* M座標の有無（取得可能なら）
* Bounding Box

Geometry Type例：

* Point
* MultiPoint
* LineString
* MultiLineString
* Polygon
* MultiPolygon
* GeometryCollection

複数のGeometry Typeが存在する場合は、

`Mixed`

または種類一覧を表示してください。

---

# 12. Vector属性情報

Vectorの場合は属性情報も表示してください。

例：

| フィールド | 型       |
| ----- | ------- |
| id    | Integer |
| name  | String  |
| area  | Real    |
| date  | Date    |

最低限：

* フィールド名
* データ型

を確認できるようにしてください。

属性値そのものを大量表示する必要はありません。

今回は属性テーブルビューアを作ることが目的ではありません。

---

# 13. Rasterの場合

Rasterと判定した場合は、以下を可能な範囲で表示してください。

## ラスタ情報

* Width
* Height
* バンド数
* Pixel Size / Resolution
* Data Type
* NoData
* Bounding Box
* CRS / EPSG

可能であれば、

* Compression
* Overviewの有無

も表示してください。

---

# 14. Raster統計について

第一版では、

* Min
* Max
* Mean
* StdDev

などの全画素統計を自動計算しないでください。

大容量DEMや航空レーザ由来ラスタなどで、読み込み直後に重くなることを避けるためです。

今回のGIS Infoは、

**高速なメタデータ確認**

を優先してください。

統計計算は将来機能とします。

---

# 15. 対応形式

第一版として、可能な範囲で以下を対象にしてください。

## Vector

優先順位：

1. GeoJSON
2. KML
3. Shapefile
4. GeoPackage

## Raster

優先順位：

1. GeoTIFF
2. COG

ただし、すべてを無理に一度に実装して不安定にしないでください。

依存ライブラリやブラウザ上での実装難易度を確認し、

**確実に動く形式から段階的に実装**

してください。

---

# 16. Shapefileの扱い

Shapefileは、

* `.shp`
* `.shx`
* `.dbf`
* `.prj`

など複数ファイルで構成されるため、扱いに注意してください。

可能であれば、

* ZIP化されたShapefile
* 複数関連ファイルの同時ドロップ

のどちらかを第一版で対応してください。

無理に両方対応する必要はありません。

どちらを採用したかREADMEへ明記してください。

`.prj` が存在しない場合は、CRSを推測しないでください。

---

# 17. 大容量ファイルへの配慮

GISデータは数百MB以上になる場合があります。

そのため、

* 不要な全データコピーを避ける
* 不要な全画素走査を避ける
* UIスレッドを長時間ブロックしない
* 可能なら必要なメタデータだけ取得する

構成にしてください。

巨大ファイルを完全にメモリ展開する設計は可能な限り避けてください。

ただし第一版でWeb Workerまで過剰実装する必要はありません。

---

# 18. エラー処理

以下を適切に扱ってください。

* 未対応形式
* ファイル破損
* CRS情報なし
* 解析不能
* 関連ファイル不足
* 空ファイル
* 想定外のデータ

エラー時でもアプリ全体を停止させないでください。

右側または左側に、

`このファイル形式には現在対応していません`

など、ユーザーが原因を理解できる表示をしてください。

---

# 19. ファイル差し替え

一度ファイルを読み込んだ後でも、

別のファイルを右側へドロップすれば、

現在の情報をクリアして新しいファイルを解析してください。

ページ再読み込みは不要としてください。

# 31. 実装ライブラリの選定

Vector / Rasterをブラウザ上で扱うために追加ライブラリが必要な場合は、まず候補を比較してください。

判断基準：

1. ブラウザで動作する
2. GitHub Pagesで利用できる
3. 独自バックエンド不要
4. 現在も利用可能なライブラリ
5. 不要に巨大な依存を増やさない
6. Vector / Rasterの情報取得に十分
7. 大容量GISファイルへの影響

ライブラリ追加前に、

* 何を追加するか
* なぜ必要か
* 他の候補
* bundleサイズやWASMへの影響

を簡潔に整理してください。

特にGDAL / WebAssembly系を導入する場合は、単純なライブラリ追加より影響が大きいため、必要性を確認してから採用してください。

可能なら、

**軽量な形式は専用ライブラリで処理し、GDAL/WASMを安易に全処理の前提にしない**

構成も検討してください。
